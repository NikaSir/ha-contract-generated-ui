# Generated Subpanel Shell v1

**Status:** canonical application-subpanel architecture for Contract Generated UI  
**Owner:** `ha-contract-generated-ui`  
**First demonstrations:** ZONT and StarLine

## Decision

Application subpanels are generated by Contract Generated UI. Home Assistant integrations own domain data and commands; they do not own application-shell geometry.

The boundary is:

```text
Home Assistant integration
  └─ entities / states / services / buttons / events

Contract Generated UI
  └─ contracts
  └─ semantic inventory
  └─ panel manifests
  └─ navigation contract
  └─ Header / Back
  └─ Bottom Tab Bar
  └─ routes
  └─ Lovelace generation
  └─ semantic diff / release gate
```

New ZONT, StarLine and future generated subpanels do **not** get separate UI repositories.

The older `templates/integration-panel-v1/` reference remains useful for existing integration-owned custom panels during migration. It is not the preferred architecture for a new subsystem whose UI can be expressed through Contract Generated UI.

## Formal sources

Navigation is data:

```text
navigation/
└── main.yaml
```

`NavigationContract v1` owns:

- canonical route IDs;
- absolute route paths;
- parent relationships;
- global app tabs;
- embedded tab groups that are still hosted inside an existing dashboard.

A generated standalone subpanel owns its own tab list through its short `PanelManifest`. The manifest references only the navigation contract and logical parent route.

Example:

```yaml
spec:
  dashboard_path: /dashboard-starline
  subpanel:
    template: standard_v1
    navigation: main
    parent: house.vehicles
  views:
    - id: overview
      title: Обзор
      icon: mdi:view-dashboard-outline
      path: overview
      order: 0
      renderer: subpanel_placeholder_v1
      placeholder: Test shell
      modules: []
```

The same manifest model later accepts real contract modules; the shell does not change.

## Native Header and deterministic Back

Every generated subpanel view is emitted as a Home Assistant native subview:

```yaml
subview: true
back_path: /declared/parent/path
```

The view title is normalized to the subsystem title. Therefore Home Assistant owns the visible top chrome while Contract Generated UI owns the declarative parent route.

Back never depends on browser history.

## Bottom Tab Bar

The frontend does not contain subsystem-specific tab definitions.

Generation compiles:

```text
contracts + manifests + navigation
           ↓
generated/navigation.json
           ↓
nikas-ui.js
           ↓
fixed Bottom Tab Bar
```

`nikas-ui.js` reads the registry and renders 2–5 tabs with the same geometry and active-state behavior. Adding a new generated subpanel must not require editing `nikas-ui.js`.

The frontend registry contains route and presentation metadata only. It contains no Home Assistant `entity_id`, `device_id` or private inventory facts.

## Existing central electricity subpanel

Infrastructure v0.12 predated this generic mechanism. Its four power views are now described as an embedded `tab_group` in `navigation/main.yaml`.

This removes the previous hardcoded `POWER_ITEMS` JavaScript list while keeping the current dashboard URL stable.

The power content renderer remains domain-specific for now. Its navigation chrome is data-driven by the same shell as ZONT and StarLine.

## Renderer contract

`subpanel_placeholder_v1` exists only to test shell mechanics without inventing domain data.

It:

- accepts no entity modules;
- renders native Heading/Markdown cards;
- is deterministic;
- is intentionally replaced by a real renderer/contract composition when verified semantic bindings are available.

Production domain panels must never use fabricated values to make a placeholder look realistic.

## Runtime source layout

Managed public sources:

```text
/config/contract_generated_ui/
├── contracts/
├── manifests/
├── navigation/
├── inventory/        # private, never overwritten by bundled sync
├── snapshots/        # private/history, never overwritten
└── generated/
    ├── *.yaml
    ├── *.meta.json
    ├── navigation.json
    └── lovelace_configuration_snippet.yaml
```

Bundled source synchronization may update only `contracts/`, `manifests/` and `navigation/`.

## Registration

Generated standalone subpanels are registered as YAML dashboards so their routes exist, but they are emitted with:

```yaml
show_in_sidebar: false
```

Entry is through their logical parent page.

Central top-level dashboards remain visible according to their normal registration policy.

## Semantic safety

Navigation data participates in the renderer-engine fingerprint.

Changing:

- parent route;
- tab count;
- tab title;
- tab icon;
- tab route;
- shell implementation

changes the generated dashboard and/or renderer fingerprint, so the existing semantic release gate sees the change rather than treating it as formatting noise.

Entity bindings remain governed by semantic inventory exactly as before.

## Adding another subsystem

A new standalone subpanel requires data changes only:

1. define/confirm its logical parent route in `navigation/main.yaml`;
2. add a short panel manifest;
3. define 2–5 views with titles/icons/order;
4. add real contract modules when domain content is ready;
5. regenerate and pass semantic review.

No new Header implementation, Back code, Bottom Tab Bar implementation or frontend route constants are allowed.

## Acceptance checklist

A generic shell release is accepted when:

- ZONT renders four tabs;
- StarLine renders five tabs;
- both use the same native Header;
- both use explicit `back_path`;
- both use the same fixed Bottom Tab Bar;
- the active tab is unambiguous;
- `nikas-ui.js` contains neither ZONT nor StarLine route constants;
- electricity local tabs also come from the navigation registry;
- no horizontal scrolling appears on iPhone portrait;
- content scrolls above the fixed bar;
- generated subpanels remain hidden from the sidebar;
- runtime source validation includes `navigation/`;
- repository/runtime renderer sources remain parity-tested;
- CI, Hassfest and HACS validation pass.

## Architectural invariant

> One UI repository. One navigation-contract mechanism. One generated subpanel shell. New subsystems join declaratively.
