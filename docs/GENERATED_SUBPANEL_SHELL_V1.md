# Generated Subpanel Shell v1

**Status:** generated-subpanel architecture; shell geometry is governed by the newer canonical standards  
**Owner:** `ha-contract-generated-ui`  
**Canonical shell:** `SPECIALIZED_PANEL_SHELL_STANDARD.md` v1.2  
**Canonical zoom:** `SPECIALIZED_PANEL_ZOOM_STANDARD.md` v1.2

> Historical note: older revisions of this document described permanent Header Back / `back_path` behavior. That is no longer the permanent Header contract. The left Header rail is now always the Home Assistant main-system menu. A logical parent route remains useful navigation metadata, but does not replace the system menu control.

## Decision

Application subpanels may be generated by Contract Generated UI. Home Assistant integrations own domain data and commands; generated shell geometry is shared by CGUI.

The boundary is:

```text
Home Assistant integration
  └─ entities / states / services / buttons / events

Contract Generated UI
  └─ contracts
  └─ semantic inventory
  └─ panel manifests
  └─ navigation contract
  └─ safe-area policy
  └─ Header / Home Assistant menu
  └─ optional peer-device context placement
  └─ exactly one zoomable work viewport
  └─ Bottom Tab Bar
  └─ routes
  └─ Lovelace/custom-panel generation
  └─ semantic diff / release gate
```

Existing integration-owned panels can implement the same formal shell contract locally without becoming runtime-dependent on CGUI.

## Formal sources

Navigation is data:

```text
navigation/
└── main.yaml
```

`NavigationContract v1` owns:

- canonical route IDs;
- absolute route paths;
- parent relationships;
- global app tabs;
- embedded tab groups.

A generated standalone subpanel owns its tab list through its short `PanelManifest`. The manifest references navigation and its logical parent route.

Example:

```yaml
spec:
  dashboard_path: /dashboard-starline
  subpanel:
    template: standard_v1
    navigation: main
    parent: house.vehicles
  views:
    - id: overview
      title: Обзор
      icon: mdi:view-dashboard-outline
      path: overview
      order: 0
      renderer: subpanel_placeholder_v1
      placeholder: Test shell
      modules: []
```

The same manifest model later accepts verified real contract modules; the shell does not change.

## Header and logical parent navigation

The permanent Header follows the Specialized Panel Shell Standard:

```text
☰ | geometrically centered subsystem title | optional global action
```

The left control exposes Home Assistant main-system navigation.

A manifest may still declare a canonical logical parent route. That route is used for explicit domain navigation/deep-link relationships where needed, but it is not implemented as the permanent left Header control and does not depend on browser history.

Generated panels must not invent integration-specific menu drawers behind the Home Assistant menu icon.

## Safe area

Safe-area inset is consumed exactly once by the effective application boundary.

Generated shell implementation must avoid:

- Header under notch/Dynamic Island;
- double top inset / blank safe-area bands;
- Bottom Tab Bar under Home Indicator;
- device-model-specific fixed offsets.

## Bottom Tab Bar

The frontend does not contain subsystem-specific tab definitions.

Generation compiles:

```text
contracts + manifests + navigation
           ↓
generated/navigation.json
           ↓
shared shell frontend
           ↓
fixed Bottom Tab Bar
```

The shell reads registry/manifest data and renders 2–5 primary tabs with common geometry and active-state behavior. Adding a generated subpanel does not require adding subsystem route constants to generic frontend code.

The frontend registry contains route/presentation metadata only. It contains no private Home Assistant entity/device inventory facts.

## Exactly one zoomable work viewport

Generated specialized panels use one and only one work viewport for domain scaling.

The following remain native-scale:

- Header / HA menu;
- persistent peer-device selector when present;
- optional zoom controls;
- Bottom Tab Bar.

The shell reconciler must be idempotent across Home Assistant rerenders and unrelated state changes. It must not create nested zoom wrappers, duplicate controls or progressive content shrinking.

Pinch/persistence details are defined by `SPECIALIZED_PANEL_ZOOM_STANDARD.md` v1.2.

## Optional zoom controls

Two-finger focal-point pinch is mandatory on touch clients.

On-screen `− / percentage / +` controls are an optional shell presentation. If enabled they are shell-owned, native-sized, unique and outside the work viewport.

Gesture-only mobile presentation is conforming when declared and field-accepted.

## Peer-device context

When a generated application represents multiple peer physical devices, a persistent Device Selector may be placed directly below Header.

Required behavior follows the canonical shell:

- fixed peer order;
- native scale;
- preserve selected peer across Bottom Tab changes;
- selected-device-only primary content;
- no full duplicate blocks for non-selected peers.

Subordinate channels are not automatically peer devices.

## Existing central electricity subpanel

Infrastructure power views predate this generic mechanism and remain an embedded tab group described by navigation data. Domain-specific power rendering may remain separate while navigation chrome follows common contracts.

## Renderer contract

`subpanel_placeholder_v1` exists only to test shell mechanics without inventing domain data.

It:

- accepts no fabricated entity modules;
- renders deterministic placeholder content;
- is replaced by real renderer/contract composition when verified semantic bindings exist.

Production domain panels must never use fabricated values to make placeholders look realistic.

## Runtime source layout

Managed public sources:

```text
/config/contract_generated_ui/
├── contracts/
├── manifests/
├── navigation/
├── inventory/        # private, never overwritten by bundled sync
├── snapshots/        # private/history, never overwritten
└── generated/
    ├── *.yaml
    ├── *.meta.json
    ├── navigation.json
    └── lovelace_configuration_snippet.yaml
```

Bundled synchronization may update only public managed source kinds. Private inventory and snapshots remain outside public source replacement.

## Registration

Generated standalone specialized applications are registered at stable routes according to their implementation type. Sidebar exposure is a separate policy from application-shell navigation.

A logical parent route remains metadata for central-panel deep links and domain navigation relationships.

## Semantic safety

Navigation/shell metadata participates in renderer/release fingerprints where applicable.

Changing parent routes, tab count/title/icon/path or shell implementation must not be treated as formatting noise.

Entity bindings remain governed by semantic inventory.

## Adding another subsystem

A new generated standalone subpanel requires principally data/contract changes:

1. confirm logical route/parent in navigation data;
2. add short panel manifest;
3. define 2–5 primary views;
4. add verified domain contract modules;
5. use canonical shell v1.2;
6. regenerate and pass semantic/UI review.

No subsystem-specific Header/menu/safe-area/zoom/Bottom-Bar implementation is allowed in generic generated frontend code.

## Acceptance checklist

A generated specialized shell release is accepted when:

- permanent left Header control is Home Assistant system menu;
- title is geometrically centered;
- safe area is consumed exactly once;
- Bottom Tab Bar comes from declarative navigation data;
- active tab is unambiguous;
- exactly one work viewport exists;
- repeated Home Assistant updates do not nest shell wrappers;
- pinch/pan/persistence works on target touch client;
- optional zoom controls, if enabled, appear exactly once;
- no horizontal clipping exists at 100% mobile layout;
- content clears fixed Bottom Tab Bar;
- no fabricated domain data exists;
- runtime source validation includes navigation;
- repository/runtime renderer parity tests pass;
- CI, Hassfest and HACS validation pass;
- actual target-device field acceptance is completed.

## Architectural invariant

> One navigation-contract mechanism and one canonical specialized-panel shell. Generated subsystems join declaratively; the permanent HA menu, safe areas, peer context placement, exactly one zoom work viewport and Bottom Tab Bar are shell responsibilities rather than domain code.
