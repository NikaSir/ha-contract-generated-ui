# Home Assistant NikaS — единый UI-стандарт специализированных панелей

**Статус:** Normative  
**Версия:** 1.1  
**Дата:** 2026-08-22

Этот документ обязателен для integration-owned панелей Home Assistant NikaS. Он дополняет ADR-001 и определяет общую оболочку мобильного приложения; предметное содержание остаётся ответственностью интеграции-владельца.

## 1. Основной сценарий

Первичный target: **iPhone Pro Max · portrait · управление одной рукой**.

Специализированная панель должна восприниматься как самостоятельное мобильное приложение внутри Home Assistant, а не как обычный Lovelace dashboard. Полив, S8 OMNI, Keenetic и UPS имеют разную предметную модель, но используют одинаковую навигационную механику и базовый визуальный язык.

## 2. Обязательная структура

Каждая специализированная панель имеет три постоянных уровня:

1. **Header** — выход из панели и максимум 1–2 действительно глобальных действия.
2. **Content** — состояние, управление, телеметрия, workflow, история и диагностика текущего раздела.
3. **Fixed bottom Tab Bar** — переключение основных разделов внутри этой панели.

Ключевой контракт:

> **Header = выйти из панели. Bottom Tab Bar = перемещаться внутри панели.**

Каноническая схема:

```text
┌─────────────────────────────────┐
│ ←  Название панели          ⟳ ⋮ │
├─────────────────────────────────┤
│                                 │
│        ТЕКУЩИЙ ЭКРАН            │
│                                 │
│        СТАТУС                   │
│        УПРАВЛЕНИЕ               │
│        ТЕЛЕМЕТРИЯ               │
│                                 │
│        vertical scroll          │
│                                 │
├─────────────────────────────────┤
│  Обзор │ Раздел │ Раздел │ Диаг.│
└─────────────────────────────────┘
             iOS Safe Area
```

## 3. Унифицированный Header

На каждом основном view присутствует один и тот же логический Header.

Обязательно:

- слева `mdi:arrow-left`;
- touch target Back ориентировочно не менее 44×44 pt;
- далее название системы/устройства;
- допускается компактная иконка интеграции;
- версия UI/интеграции — только secondary text;
- справа максимум 1–2 глобальных action: например `Обновить` или `⋮`, если действие действительно существует.

Header и его кнопки не выполняют entity-specific действия по hold/double tap.

### 3.1. Back — только explicit navigation

Back **не использует browser history**. Причина: специализированная панель может открываться из House, Actions, Infrastructure, sidebar, уведомления или deep-link, поэтому предыдущая запись браузерной истории не является приложенческим контрактом.

Зафиксированные parent routes:

| Панель | Explicit Back target |
| --- | --- |
| HO-SC-8W / Полив | `/dashboard-actions` |
| S8 OMNI | `/dashboard-actions` |
| Keenetic Hero 4G+ | `/dashboard-infrastructure/overview` |
| Stark SolarPower UPS | `/dashboard-infrastructure/overview` |

## 4. Fixed bottom Tab Bar

Все основные разделы панели располагаются **только** в нижней navigation bar.

Требования:

- фиксирована у нижней границы viewport при вертикальной прокрутке;
- занимает всю полезную ширину мобильного viewport;
- является частью оболочки приложения, а не плавающей карточкой поверх content;
- нижняя кромка Tab Bar примыкает к нижней границе viewport / iOS safe area без визуального зазора;
- учитывает `env(safe-area-inset-bottom)` и боковые safe-area iOS;
- имеет одинаковую базовую высоту и геометрию во всех specialized panels;
- крупные touch targets, ориентир — не менее 44 pt, предпочтительно 52–56 px для primary nav item;
- иконка + короткое название;
- активный раздел визуально однозначен внутри общей панели;
- 3–5 основных разделов;
- если разделов больше пяти, второстепенные функции уходят в `Ещё`, `Сервис`, `Диагностика` или drill-down;
- нижняя панель не перекрывает последний content: рабочая область имеет достаточный bottom padding, чтобы последняя карточка полностью прокручивалась выше Tab Bar;
- bottom navigation не вызывает more-info и не управляет устройством.

### 4.1. Edge-attached, а не floating

Канонический мобильный вариант — **полноширинная edge-attached нижняя панель**.

Не допускается primary navigation в виде floating/pill-карточки с внешними боковыми/нижними отступами, которая визуально лежит поверх content. В частности, для iPhone нельзя использовать модель вида:

- `width: calc(100% - 20px)`;
- `bottom: 8px`;
- отдельная округлая карточка со сквозным скруглением всех четырёх углов.

Допустима адаптация ширины на iPad/desktop, но mobile layout остаётся эталоном: Tab Bar прикреплена к нижней границе и занимает всю полезную ширину приложения.

Рекомендуемая геометрия mobile shell:

- `position: fixed`;
- `left: 0` / логически полноширинная область приложения;
- `bottom: 0`;
- `width: 100%` в mobile viewport;
- верхние углы могут иметь мягкое скругление;
- нижние углы не должны создавать эффект отдельной плавающей карточки;
- нижний padding включает `env(safe-area-inset-bottom)`.

### 4.2. Активная вкладка

Активный раздел обозначается **внутри общей нижней панели**.

Предпочтительно:

- лёгкий фон active area;
- акцентный цвет иконки;
- акцентный цвет текста;
- мягкое локальное скругление active area допустимо.

Не следует визуально «вынимать» активную вкладку из Tab Bar или превращать её в отдельную floating-card.

## 5. Верхние primary-tabs запрещены

Основные переключатели вида:

`Обзор | Диагностика | История`

или

`Обзор | Зоны | Программы | Диагностика`

не используются сверху как primary navigation. Их функция переносится в fixed bottom Tab Bar.

После Header пользователь должен как можно быстрее увидеть **главное предметное состояние**, а не второй слой навигации.

## 6. App-like behavior

Внутренние разделы (`Обзор → Зоны → Программы`, `Обзор → Уборка → Станция` и т. п.) — экраны одного приложения. Header остаётся логически постоянным.

`← Back` всегда выходит к зафиксированному parent route и **не** является переключателем предыдущей внутренней вкладки.

## 7. Не дублировать крупный заголовок

Header сообщает, **где** пользователь находится. Hero-card сообщает, **что сейчас происходит**.

Не следует одновременно выводить крупное имя устройства в Header и ещё раз крупным заголовком в hero-card. Версию UI/интеграции показывать мелким secondary text либо в Диагностике.

## 8. Mobile-first acceptance

Приёмка обязательна на iPhone Pro Max portrait. Desktop/iPad не заменяют мобильную проверку.

Не допускается:

- горизонтальный скролл;
- обрезанные до непонятного состояния подписи;
- нижняя навигация, исчезающая при длинной прокрутке;
- floating Tab Bar поверх content;
- критический content под bottom bar;
- чрезмерно высокий Header;
- слишком близко расположенные критические кнопки.

Вертикальная прокрутка должна быть естественной. Основные функции должны быть достижимы одной рукой.

## 9. Единая визуальная идентичность

Панели не обязаны выглядеть одинаково. Предметная идентичность сохраняется.

Одинаковыми должны быть:

- расположение и семантика Header;
- Back слева;
- геометрия touch targets;
- полноширинный fixed bottom Tab Bar;
- базовая высота Tab Bar и логика safe-area;
- active-tab indication;
- explicit parent navigation;
- `unknown/unavailable` semantics;
- long press behavior фактических entity.

Формула: **единая оболочка приложения + специализированное содержимое**.

## 10. Long press

Для фактических Home Assistant entity действует проектное правило:

> **Long press → штатный Home Assistant more-info.**

Header и bottom navigation являются навигационными элементами и entity-specific действий не выполняют.

## 11. Safety invariants

Перестройка UI не изменяет границы безопасности интеграций.

Запрещено:

- raw Tuya DP из frontend;
- прямой RCI/SNMP write из панели;
- обход публичного API интеграции;
- неподтверждённые управляющие действия;
- фиктивные entity/action;
- интерпретация `unknown`/`unavailable` как нормы;
- устройство-команда, замаскированная под декоративный элемент Header.

## 12. Требования по текущим integration-owned панелям

### Stark SolarPower

Header:

`←  Stark SolarPower                         ⟳`

Secondary: `UPS · UI vX.X.X`

Bottom nav:

`Обзор · Диагностика · История`

Back: `/dashboard-infrastructure/overview`.

Существующий предметный Overview (`Сеть → UPS → Нагрузка`, АКБ, нагрузка, freshness, два UPS) является принятой базой и не требует концептуального redesign.

### S8 OMNI

Рекомендуемый bottom nav:

`Обзор · Уборка · Станция · Сервис · Диагн.`

Back: `/dashboard-actions`.

Hero должен прежде всего показывать composite state (`На базе · Заряжен`, уборка, возврат, операция станции), а не повторять крупное имя `S8 OMNI` из Header.

### HO-SC-8W / Полив

Header:

`←  Полив`

Secondary: `INKBIRD / HiOazo · HO-SC-8W`.

Bottom nav:

`Обзор · Зоны · Программы · Диагн.`

Back: `/dashboard-actions`.

Primary navigation должна быть только в нижней полноширинной Tab Bar.

### Keenetic Hero 4G+

Панель при первой реализации сразу строится по этому стандарту.

Header:

`←  Keenetic Hero 4G+                         ⟳ / ⋮`

Back: `/dashboard-infrastructure/overview`.

Рекомендуемый bottom nav:

`Обзор · WAN/LTE · Трафик · Диагн.`

или, если отдельный failover-screen действительно содержателен:

`Обзор · WAN/LTE · Failover · Трафик · Диагн.`

Первый экран: Интернет → активный WAN → Ethernet → LTE → последнее переключение. Системные параметры роутера не должны вытеснять эксплуатационное состояние.

## 13. Критерий готовности

Специализированная панель считается приведённой к стандарту только если одновременно выполняется всё:

- сверху есть явный Back с explicit parent route;
- Header не используется для внутренних вкладок;
- primary section navigation находится в полноширинной fixed bottom Tab Bar;
- Tab Bar примыкает к нижней границе viewport и не оформлена как floating card поверх content;
- active tab обозначен внутри общей Tab Bar;
- bottom bar остаётся доступным при длинной прокрутке;
- iOS safe area обработана;
- последний content полностью прокручивается выше Tab Bar;
- после Header первым виден предметный статус;
- `unknown/unavailable` не маскируются;
- фактические entity сохраняют long press → more-info;
- frontend не обходит safety/API интеграции;
- приёмка выполнена на iPhone Pro Max portrait.

Если основной переключатель разделов остаётся сверху, отсутствует explicit Back, bottom navigation пропадает при прокрутке **или bottom navigation выполнена как плавающая карточка поверх content**, панель **не соответствует** UI-стандарту Home Assistant NikaS.
